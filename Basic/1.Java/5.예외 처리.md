## 예외 계층(Throwable, Error, Exception)
- Error
	- 애플리케이션이 아닌 서버에 발생한 오류
		- e.g. OutOfMemoryError
	- 애플리케이션에서 처리할 필요가 없고 처리해서도 안됨

## Checked vs Unchecked 예외
- Unchecked (런타임)
	- `RuntimeException`을 상속한 예외
	- 명시적인 예외 처리 코드 필요 없음
	- throws 선언은 가능 (클라이언트가 처리할 필요는 ❌)
	- 개발자의 로직 처리, 사용자의 입력 오류 등 '피할 수 있는 상황'에 발생
- Checked
	- `RuntimeException`을 상속하지 않은 예외
	- 예외 처리 코드(throws 던지기 / try-catch)를 작성하지 않으면 컴파일 에러 발생
	- 처리 강제로 인한 **무한 throws 지옥** 등 비효율을 이유로 현재는 사용하지 않는 추세

## 예외 전파·변환
- 전파: catch한 예외를 단순히 re-throw (+ 로그 출력 등 부가 동작)
- **변환 (포장)**
	- catch한 예외에 좀 더 구체적인 의미를 부여
		- e.g. `SQLException` → `DuplicateOrderException`
	- **Checked 예외를 Unchecked 예외로 전환**
		- 복구 불가능한 예외라면 빠르게 런타임 예외로 포장해 

## 예외 처리 모범 사례
- **커스텀 예외 작성 시 체크/런타임 선택**
	- 예외 포장 목적
		- 런타임(어디서든 처리할 수 있도록)
		- throws 선언 (클라이언트에 정보 전달용)
	- `애플리케이션 예외`
		- 비즈니스 로직에서의 비정상 케이스 분기를 위해 일부러 발생시키는 커스텀 예외
		- **체크** 예외 → 처리 코드 작성을 강제
- 예외 변환 시 하위 에러를 감싸서 중첩 예외로 던지기
	- ```java
	  catch(SQLException e) {
	    throw DuplicateOrderException(e);
	    // 또는
	    throw DuplicateOrderException().initCause(e);
	  }
	  
	  // 근본 원인은 getCause()로 확인
	  ```
