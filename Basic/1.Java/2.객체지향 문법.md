## 클래스와 객체
- 클래스: 객체의 설계도. 필드와 메소드를 멤버로 가짐
- 객체: 클래스를 기반으로 생성된 인스턴스. heap 영역에 할당

## 상속
- 부모 클래스의 private 제외한 멤버를 자식 클래스가 물려받는 것
- 클래스는 다중 상속 불가
- **인터페이스는 다중 상속 가능**
- 모든 클래스는 Object를 상속받음
- **"is-a" 관계일 때만 상속을 쓰기. 그 외의 경우 composition으로 대체 가능**
- 어떤 클래스가 상속 목적이 아닌 경우 final 붙여서 상속을 막는 것도 권장
- 더 알아보기) `sealed` 란?

## 다형성
- 호출은 동일하지만 여러 방식으로 동작할 수 있는 성질
- '상위 타입 (인터페이스 등) 기반으로 구현체 갈아끼우기'
- 호출부는 구현체를 몰라도 된다는 장점이 있다
- 스프링의 의존성 주입과 대부분의 디자인 패턴은 다형성을 활용
- 코드에 instanceof 연산이 많다면 다형성 활용이 빈약하다는 신호

## 추상화(추상 클래스 vs 인터페이스)
- 세부사항을 숨기는 것. 범용적인 의미로 쓰이기 때문에 자바에서 어떻게 구현하는지만
- 추상 클래스 (extends)
	- **필드를 가질 수 있다**
	- 구현 없는 추상 메소드를 선택적으로 선언할 수 있다
	- **생성자를 가질 수 있다** (자식에서 호출용)
	- "공통 상태 + 일부 구현을 공유하는 계층 구조"에 주로 사용 (is-a)
- 인터페이스 (implements)
	- ~~모든 메소드가 public + 추상 메소드~~
	- default 메소드 (구현부 작성) 메소드 가능
		- 인터페이스에 새 메소드 추가 시 구현체 호환성이 깨지는 문제를 해결하기 위한 수단
	- static 메소드 가능
	- private 메소드 가능
		- default, static 메소드 중복 제거용
	- **다중 구현이 가능하다**
	- 상수를 가질 수 있다
	- **"서로 관계없는 클래스들에 공통 행동 계약을 부여"할 때 주로 사용 (can-do)**
	- 웬만한 경우에 인터페이스를 쓴다

## 캡슐화
- 객체 필드를 외부로부터 숨기고 제한된 접근 방식만 열어두기
- 접근제어자와 getter setter
- setter는 필요한 경우만. DTO, VO는 record 및 정적 팩토리 메소드 권장
- Bean Validation 뿐만 아니라 setter 내부에서 인자 검증하는 것을 권장

## 오버로딩 vs 오버라이딩
- 오버로딩: 이름이 같지만 시그니처 (이름, 파라미터 타입, 개수, 순서)가 다른 메소드를 여러 개 정의하는 것
- 오버라이딩: 자식 클래스가 부모의 동일 시그니처 메소드를 덮어 쓰는 것
	- **반환 타입은 같거나 더 좁게 (covariant return type)** → ❌ 부모는 Bird, 자식은 Animal을 반환
	- **접근 제어자는 부모와 같거나 더 넓게** → ❌ 부모는 public, 자식은 private
	- **던지는 checked exception은 같거나 더 좁게** → 부모는 IOException, 자식은 Exception
	- 왜?
		- **호출부는 상위 타입의 반환타입/제어자/throws만 보고 코드를 작성한다**
		- 런타임에 동작이 깨진다
			- `Parent p = new Child(); Bird b = p.getBird(); // 실제 반환은 Animal`
	- 이 조건 어길 시 컴파일 단계에서 실패
	- 리스코프 치환 원칙 (LSP): 부모 타입으로 다루는 코드가 자식 인스턴스로 바뀌어도 깨지면 안 된다 = 배신때리지 말아라

## 생성자와 초기화 순서
- 객체를 생성할 때 호출되는 특수 메소드
- 자식 생성자는 super를 명시하지 않을 경우 부모의 no-arg 생성자를 호출한다
- 생성자에서 super든 this든 다른 생성자를 선언하려면 생성자 맨 앞에 1번만 할 수 있다
- 필드가 많고 생성자가 복잡해지면 Builder 패턴을 고려
	- Lombok @Builder는 특정 메소드를 override 가능
	- 일부 프레임워크는 특정 생성자가 존재해야 동작함에 유의

**자식 클래스 초기화 순서**
1. 부모 클래스의 정적(static) 필드 초기화 + 정적 초기화 블록 (클래스 로딩 시 최초 1회만, 객체 생성과 무관)
2. 자식 클래스의 정적 필드 초기화 + 정적 초기화 블록 (최초 1회만)
3. 부모 클래스의 생성자 호출
	- 부모의 인스턴스 필드 초기화 → 부모의 생성자 본문
4. 자식 클래스의 인스턴스 필드 초기화 → 자식의 생성자 본문
- **필드 초기화가 먼저, 부모가 먼저**
- 인스턴스 초기화 블록도 있는데 사실상 안 쓴다
	- 그나마 쓰는 케이스: 이중 중괄호 초기화
	- ```java
	  new ArrayList<String>() {{ add("a"); }};
	  
	  new ArrayList<String>() { // 바깥쪽 중괄호: ArrayList의 익명 자식 클래스 선언
		  { // 안쪽 중괄호: 인스턴스 필드 초기화 → 익명 클래스라 생성자 정의가 불가
		    add("a");
		  }
	  }
	  ```
	  - 이마저도 제대로 제어하지 못하면 메모리 누수 위험이 있고, 현재는 Map.of() 같은 초기화 메소드를 제공하기 때문에 현재는 안 쓴다고 보면 된다

## 내부 클래스
- 인스턴스 멤버 클래스
	- static 없이 클래스 내부에 선언
	- 바깥 인스턴스를 생성해야만 내부 인스턴스를 생성할 수 있음
	- 바깥 클래스의 멤버에 접근 가능
	- **주로 바깥 클래스 내부에서만 사용하는 용도 → private으로 선언하는 게 일반적**
	- 바깥 인스턴스 참조를 들고 있으므로 메모리 누수 위험이 있음
- **정적 멤버 클래스**
	- static으로 클래스 내부에 선언
	- 내부 인스턴스만 별도 생성 가능
	- 바깥 클래스의 정적 멤버에만 접근 가능
	- 특정 클래스와 함께 자주 쓰이는 클래스나 Nested 관계 클래스를 정의하기 위해 종종 사용
	- **멤버 클래스가 필요한 경우 가급적이면 정적 멤버 클래스로**
- 지역 클래스
	- 메소드 안에서 정의하는 클래스
	- 복잡한 기능을 구현할 클래스가 필요한데 정말 해당 메소드에서만 필요한 경우
- 익명 클래스
	- 주로 1회용 구현체 선언에 사용
	- **람다로 대체되는 경우가 많으나 메소드가 여러 개거나 필드가 필요한 경우에는 익명 클래스만 가능**
- 클래스명
	- 멤버 클래스: A$B.class
	- 지역 클래스: A$1B.class
	- 익명 클래스: A$1.class
