## JDBC 기본 흐름

## `DataSource`
- DB 커넥션 획득, 풀링 등의 기능을 추상화한 인터페이스
- 잘 구현된 클래스들이 많아 직접 구현할 일 거의 없음
- 로컬 개발용: `SimpleDriverDataSource`

## 커넥션 풀 개념
- Connection 객체를 지정한 수만큼 미리 생성해서 보유한다. 매번 새로 생성하는 비용을 절감할 수 있다
- close()를 통한 자원 반납이 필수
	- DataSource.getConnection() 이후 반납을 하지 않으면 커넥션이 모두 고갈되어 DB 연결이 불가능
- 반납 코드 구현하기
	- 쿼리 실행 중 예외가 발생하면 close 호출이 불가 → finally에서 호출
	- 커넥션 획득 자체가 실패하면 close 호출이 불가 → null 확인이 우선
	- PreparedStatement, ResultSet 같은 객체를 함께 사용하면 동일한 작업이 필요 (생성의 역순)
	- close 중 예외 발생 시 다음 자원 close 호출이 불가 → 추가 catch가 필수
- 결과물
	- ```java
	  Connection conn;
	  PreparedStatement ps;
	  
	  try {
	    conn = dataSource.getConnection();
	    ps = conn.prepareStatement(...);
	    ps.executeQuery();
	  } catch (SQLException e) {
	    throw e;
	  } finally {
	    if (ps != null) {
	      try {
	        ps.close();
	      } catch (SQLException e) {}
	    }
	    if (conn != null) {
	      try {
	        conn.close();
	      } catch (SQLException e) {}
	    }
	  }
	  ```

## `JdbcTemplate`
- 위의 자원 반납 코드는 필수 → 쿼리를 실행하는 모든 메소드에 포함되어야 함
- 하나라도 실수하면 장애가 발생하기 십상 & 코드 중복이 많아 문제 식별도 어려움
- 반복되는 기능을 OCP 원칙에 의거하여 '템플릿'으로 추출
	- 사용자 (= 클라이언트) (= JdbcTemplate 호출하는 Service)는 달라지는 부분 (쿼리)만 바꾼다
- 확장성을 고려한 설계
	- 기본 [[2.디자인 패턴#전략|전략패턴]]
		- **`Strategy` 인터페이스를 구현**해 Context에 전달한다 = 매 쿼리마다 구현체 **클래스가 필요**
		- 쿼리에 DTO 등 추가 데이터가 사용될 경우 전략 구현체에 전달할 방법 (생성자 + 인스턴스 변수 등)이 필요
	- 개선
		- 구현체 클래스를 **메소드 내부의 클래스 (또는 람다)** 로 작성한다
			- 어차피 해당 메소드에서만 사용됨
			- 로컬 클래스 특성상 선언된 메소드의 변수 (DTO)에도 접근 가능
				- 해당 변수는 반드시 final
			-  `템플릿/콜백 패턴`이라고도 부름
				- 익명 클래스 → 콜백 (템플릿이 호출할, '바뀌는 부분')
				- **사용자는 템플릿에 콜백 생성에 필요한 정보만 전달** → 템플릿이 내부에서 콜백 생성해서 컨텍스트 처리 + 콜백 상호작용
				- 전략 패턴을 기반으로 스프링에서 주로 활용하는 기법
					- "DI 방식의 전략 패턴"
				- 스프링에서 제공하는 XxxTemplate, XxxCallback은 대부분 템플릿/콜백 패턴
		- 제너릭
			- 
	- 코드 예시 (토비의 스프링 3.1 3장)
- 활용
	- `update(String query)`
	- `queryForXxx(String query, Object... params)`
	- `queryForObject(String query, Object[] params, RowMapper<T> mapper)`
		- 조회 결과가 없으면 `EmptyResultDataAccessException`
