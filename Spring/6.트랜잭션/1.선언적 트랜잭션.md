## 선언적 vs 프로그래밍 방식 트랜잭션
- 프로그래밍 방식
	- 비즈니스 코드 안에서 트랜잭션 시작·커밋·롤백을 직접 호출한다
	- 사용 도구: `PlatformTransactionManager`, `TransactionTemplate`
	- 장점: 트랜잭션 범위를 코드 단위로 세밀하게 제어할 수 있다
	- 단점: 비즈니스 로직과 트랜잭션 코드가 섞이고, 서비스마다 비슷한 코드가 반복된다
- 선언적 방식
	- 트랜잭션 적용 대상과 속성(전파, 격리 수준, 롤백 규칙 등)을 코드 밖에서 선언한다
	- 대표: `@Transactional`. 스프링이 AOP 프록시로 경계 설정 코드를 대신 실행한다
	- 장점: 비즈니스 코드에는 로직만 남고, 트랜잭션 설정이 한곳에 모인다
	- 단점: 경계가 보통 메서드 단위라서 메서드 안의 일부 구간만 묶기는 어렵다
- 실무에서는 선언적 방식이 기본이고, 세밀한 제어가 필요한 곳에만 `TransactionTemplate`을 쓴다

## `PlatformTransactionManager`
- 스프링이 제공하는 **트랜잭션 경계 설정을 위한 인터페이스**
- 도입 배경
	- 트랜잭션은 DB에 국한된 개념이 아님
	- JDBC, JPA, 하이버네이트, JMS (메세징시스템 API), JTA (글로벌 트랜잭션 관리 API)... 모두 트랜잭션 관리 기능을 제공
	- 각자 관리 방식이 다르다 (Connection, TransactionManager, Session ...)
	- 트랜잭션 관리 기능은 서비스 계층이 담당해야함 [[7.트랜잭션 경계 설계#서비스 계층에 트랜잭션 적용|(관련 설명)]]
	- **따라서 트랜잭션 관리가 필요한 경우, DAO 등 infra 계층을 추상화해도 사용 기술에 따라 서비스 계층을 바꿔야 한다**
- `PlatformTransactionManager`를 사용하면 기술에 무관하게 공통된 API로 트랜잭션을 관리할 수 있다
- 주요 사용
	- 생성: 트랜잭션 관리에 사용할 기술에 따라 **생성자주입** 권장
	- 대표 구현체
		- DataSourceTransactionManager
		- JpaTransactionManager
	- 트랜잭션 획득: `TransactionStatus getTransaction(TransactionDefinition)`
		- 전파 속성·격리 수준·타임아웃·readOnly를 담는 객체
	- 커밋, 롤백:
		- `PlatformTransactionManager.commit(TransactionStatus)`
		- `PlatformTransactionManager.rollback(TransactionStatus)`
- 참고사항
	- commit(status)는 rollback-only로 표시된 트랜잭션이면 커밋 대신 롤백
		- 새 트랜잭션이 아니면(참여 중이면) 커밋을 건너뜀
		- commit()이 예외를 던진 뒤에 rollback()을 부르면 IllegalTransactionStateException 발생
